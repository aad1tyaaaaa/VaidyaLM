    # VaidyaLM — Build Plan

> **VaidyaLM**: a health-domain LLM fine-tuning project with an automated ETL and evaluation pipeline.
> *Vaidya* (वैद्य) = physician. The parts: a small LLM fine-tuned with QLoRA on medical QA, an Apache Airflow pipeline that turns unstructured medical text into instruction data, and an automated benchmark that measures the gains.

---

## 1. Goals and target outcomes

| Goal | Metric | Target |
|---|---|---|
| Improve contextual accuracy on medical QA | PubMedQA (`pqa_labeled`) accuracy + macro-F1, base vs fine-tuned | ≥15% relative improvement |
| Automate preprocessing + benchmarking | Wall-clock time: naive sequential script vs Airflow pipeline (avg of 3 runs) | ≥25% reduction |
| Reproducibility | One command to rerun the ETL, one to rerun eval; all runs logged | Done |

**Rule:** report only measured numbers. Say whether each gain is relative or absolute.

---

## 2. Tech stack

| Layer | Choice |
|---|---|
| Base model | `Qwen/Qwen2.5-1.5B-Instruct` (fallback: `meta-llama/Llama-3.2-1B-Instruct`) |
| Fine-tuning | `transformers`, `peft` (LoRA), `bitsandbytes` (4-bit QLoRA), `trl` (`SFTTrainer`), `accelerate` |
| Orchestration | Apache Airflow (official `docker-compose`), TaskFlow API + dynamic task mapping |
| ETL | `pandas`, `pyarrow`, `lxml`, `beautifulsoup4`, `datasketch` (MinHash dedup), `pydantic` (schema validation) |
| Data storage | Parquet locally + Hugging Face Datasets Hub |
| Experiment tracking | MLflow (runs in the same docker-compose) |
| Compute | Local VS Code for code, Airflow and ETL; Kaggle/Colab T4 for training and GPU inference |
| Versioning | GitHub (code), HF Hub (datasets + LoRA adapters) |

---

## 3. Data

| Dataset | Role | Notes |
|---|---|---|
| **MedQuAD** (NIH, XML) | Unstructured source → instruction pairs | ~47k Q&A pairs across XML files; needs parsing/cleaning |
| **PubMed abstracts** (subset) | Unstructured source → synthetic QA pairs | Generated by a larger model, then filtered |
| **PubMedQA `pqa_artificial` / `pqa_unlabeled`** | Training data | Context + question + answer format |
| **PubMedQA `pqa_labeled`** (1k) | **Test set only** | ❌ Never used in training or prompt tuning |

Hold out 100 examples from the training mix as a dev set for prompt and hyperparameter tuning.

## 5. Phases

### Phase 0: Setup (Day 1)
- [ ] Create GitHub repo `vaidyalm`, add `.gitignore` (data/, mlruns/, .env)
- [ ] Install Docker Desktop (+ WSL2 on Windows); start Airflow from the official `docker-compose.yaml`
- [ ] Add an MLflow service to compose; confirm both UIs load (Airflow :8080, MLflow :5000)
- [ ] Create HF account + write token; Kaggle account with phone verification (needed for GPU)
- [ ] Python env locally with `requirements.txt`

### Phase 1: Baseline evaluation (Days 2–3)
- [ ] `src/eval/prompts.py`: 3 templates
  - zero-shot
  - few-shot (3 examples from the dev set)
  - structured: "Answer using only the context. Output `Answer: yes|no|maybe` then a one-line reason."
- [ ] `src/eval/scorer.py`: parse the answer label, compute accuracy, macro-F1, parse-failure rate
- [ ] Run the base model × 3 prompts on `pqa_labeled` (Kaggle GPU)
- [ ] Log to MLflow; save `results/baseline.csv`
- **Exit criterion:** baseline numbers recorded. Every later claim is compared against this.

### Phase 2: Naive pipeline, for the timing comparison (Day 4)
- [ ] `baseline/naive_pipeline.py`: one sequential script that does ingest → parse → clean → dedupe → build pairs → eval with no caching, no parallelism and one example at a time
- [ ] Time 3 full runs; save `results/timing_naive.csv`
- Keep it honest: realistic code that's simply unoptimized, not deliberately slowed down.

### Phase 3: ETL DAG `preprocess_corpus` (Week 2)
```
ingest_raw → parse.expand(shards) → clean.expand → dedupe_minhash
          → chunk → build_instruction_pairs → validate_schema → split_and_push
```
- [ ] Shard the raw files; use `.expand()` for parallel parse/clean
- [ ] Content-hash each shard; skip unchanged shards (cache in a manifest file)
- [ ] MinHash LSH dedup (threshold ~0.85)
- [ ] Quality filters: length bounds, language check, drop answers that just repeat the question
- [ ] Synthetic pairs from abstracts: generate with a larger model, keep only pairs that pass a self-consistency/grounding check
- [ ] `pydantic` validation; failed rows go to a quarantine file with reasons
- [ ] Output train/dev parquet + push to HF Datasets (`<user>/vaidyalm-instruct`)
- [ ] Log row counts at every stage (raw → cleaned → deduped → final) to show the data funnel
- **Exit criterion:** the DAG runs end-to-end from the Airflow UI; dataset card written.

### Phase 4: Fine-tuning (Week 3)
- [ ] `src/train/sft_lora.py` driven by YAML config
  - 4-bit NF4 quantization, LoRA on `q_proj, k_proj, v_proj, o_proj`
  - r=16, alpha=32, dropout=0.05, lr=2e-4, cosine schedule, 2–3 epochs, max_seq_len 1024
  - gradient checkpointing + gradient accumulation to fit a T4
- [ ] Train in the same structured format the eval prompt uses (instruction tuning)
- [ ] Ablations: r ∈ {8, 16, 32}; data mix {MedQuAD only, + PubMedQA artificial, + synthetic}
- [ ] Push each adapter to HF Hub (`<user>/vaidyalm-qwen1.5b-lora-r16`, …)
- [ ] Log loss curves + configs to MLflow / W&B
- **Exit criterion:** at least one adapter beats the best baseline on the dev set.

### Phase 5: Eval DAG `benchmark_models` (Week 3–4)
```
list_models (base + adapters) → shard_eval_set
  → batched_inference.expand(model × shard) → score → aggregate → log_to_mlflow → report
```
- [ ] Batched generation (batch 16–32, greedy decoding, fixed seed)
- [ ] Cache predictions keyed by (model, prompt, example_id); reruns only compute what's missing
- [ ] If there's no local GPU, run the inference step on Kaggle and have the DAG pull the prediction files
- [ ] `report.py` → `results/benchmark.md` with a comparison table + confusion matrices
- **Exit criterion:** one DAG trigger produces the full comparison table.

### Phase 6: Measurement and write-up (Week 4)
- [ ] Time 3 runs of the Airflow pipeline (cold cache + warm cache, reported separately); compare with `timing_naive.csv`
- [ ] Final table: base (3 prompts) vs fine-tuned (3 prompts) × accuracy / macro-F1
- [ ] Ablation table: which part (prompting, instruction tuning, data mix) contributed what
- [ ] README: architecture diagram, how to run, results, limitations
- [ ] Optional: Gradio demo on HF Spaces

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Colab/Kaggle session drops mid-training | Save a checkpoint every N steps to `/kaggle/working`, push to HF; resume from checkpoint |
| T4 out of memory | Smaller batch + grad accumulation, gradient checkpointing, max_seq_len 768, or switch to the 1B model |
| Test-set leakage | Dedup training data against `pqa_labeled` questions/contexts (MinHash) before training |
| Fine-tune doesn't reach 15% | Tune prompts on dev, improve data quality filters, try a different data mix; report the real number either way |
| Airflow on Windows is flaky | Run inside WSL2; give Docker ≥4 GB RAM |
| Model outputs free text that won't parse | Constrained output format in training + regex parser + report parse-failure rate |
